# 第二次会后确认

## 1. 基于包的速率统计指标确认

### 1.1 新增指标

当前新增了两个基于 packet 的速率指标：

- `traffic.packet_effective_service_rate_mbps`
- `traffic.packet_effective_service_rate_per_packet_mean_mbps`

这两个指标都来自 MAC packet tracker 的整包完成事件，统计对象不是 PHY 成功解码的 TB，而是“一个 packet 的最后一个字节从当前 MAC packet queue tracker 中被扣减完成”的事件。

### 1.2 当前统计逻辑

当前 packet tracker 的统计流程如下：

1. 流量进入系统时，若某个 accepted span 的 `num_bytes > 0`，就创建一条 `PacketLifecycleRecord`，记录：
   - `packet_id`
   - `packet_size_bytes`
   - `arrival_tti`
   - `arrival_time_ms`

2. 每个 TTI 在 `RecordServedBytes()` 中，按照 FIFO 从 `mac_packet_queues[i]` 中扣减本 TTI 服务掉的字节数。

3. 当某个 packet 的 `remaining_bytes == 0` 时，认为该 packet 在当前 tracker 口径下“完成”：
   - 记录 `finish_tti`
   - 记录 `finish_time_ms`
   - 标记 `delivered = true`
   - 计算该 packet 的 `packet_system_time_ms`
   - 计算该 packet 的 `packet_rate_mbps`

4. 然后把该 packet 的统计量累计到 flow 级和 total 级：
   - `delivered_packets`
   - `delivered_bits`
   - `total_packet_system_time_ms`
   - `packet_rate_mbps_sum`

5. 仿真结束后，`TRAFFIC_PKT_RATE` 再输出两个最终指标：
   - `r_pkt_mbps`
   - `r_pkt_per_packet_mean_mbps`

### 1.3 公式定义

设第 `p` 个完成 packet 的原始 payload bit 数为 `L_p`，系统时间为 `W_p`。

当前实现里：

- `arrival_time_ms = max(arrival_tti - 1, 0) * T_slot`
- `finish_time_ms = max(finish_tti, 0) * T_slot`
- `W_p = max(finish_time_ms - arrival_time_ms, T_slot)`

其中 `T_slot` 是 slot 时长，当前 Stage-B 为 `0.5 ms`。

这里强制使用 `max(raw_system_time, 1 slot)`，是为了避免“入队与完成在同一个 slot”时出现 `0 ms` 分母，导致包级速率失真放大。

#### 指标 1：`traffic.packet_effective_service_rate_mbps`

定义为：

`R_pkt = (sum_p L_p) / (sum_p W_p)`

换成实现里的字段就是：

`traffic.packet_effective_service_rate_mbps = total_delivered_bits / total_packet_system_time`

单位是 `Mbps`。

它的统计意义是：

- 看所有已完成 packet 的总 payload bit
- 再除以这些 packet 的总 system time
- 更接近“当前 packet tracker 定义下，已完成 packet 的平均有效服务速度”

如果包长固定为 `L_pkt`，则有：

`R_pkt = L_pkt / mean(W_p)`

所以在固定包长场景下，这个指标本质上和“平均 packet system time”互为倒数，更偏向时延视角。

#### 指标 2：`traffic.packet_effective_service_rate_per_packet_mean_mbps`

先对每个完成 packet 计算：

`r_p = L_p / W_p`

再做算术平均：

`R_pkt_mean = (1/N) * sum_p r_p`

即：

`traffic.packet_effective_service_rate_per_packet_mean_mbps = (1/N) * sum_p (L_p / W_p)`

它的统计意义是：

- 每个 packet 先单独算自己的有效服务速率
- 再对这些 packet 做平均
- 会比 `R_pkt` 更偏向奖励 system time 短的 packet

在固定包长场景下，通常有：

`R_pkt_mean >= R_pkt`

原因是 `R_pkt` 对应 `L / mean(W)`，而 `R_pkt_mean` 对应 `mean(L / W)`；当存在长尾等待 packet 时，`R_pkt` 会更明显地下滑。

### 1.4 与 `traffic.served_mbps_est`、`traffic.goodput_mbps` 的对比

#### `traffic.served_mbps_est`

定义为：

- `served_bytes_est = accepted_bytes - flow_queued_bytes - mac_buffer_bytes - expired_bytes`
- `traffic.served_mbps_est = served_bytes_est * 8 / T_sim / 1e6`

它是整个仿真窗口上的系统级 aggregate served throughput estimate。

它的完成口径更接近：

- 流量已经不在当前 queueing system 中
- 不再留在 flow queue / MAC buffer
- 也没有因为 TTL 过期而被清掉

因此它是“系统排空了多少字节”的估计速率，不是 packet-centric rate。

#### `traffic.goodput_mbps`

定义为：

- `traffic.goodput_mbps = goodput_bytes * 8 / T_sim / 1e6`

其中 `goodput_bytes` 只在 `tbErr == 0` 时累计。

它的统计意义是：

- PHY 侧真正成功解码的有效 payload 吞吐
- 是系统级 aggregate goodput

因此它比 `served_mbps_est` 更严格，也更接近最终用户真正收到的有效吞吐。

### 1.5 三类指标的统计意义对照

| 指标 | 完成事件 | 分子 | 分母 | 统计意义 | 适合观察什么 |
| --- | --- | --- | --- | --- | --- |
| `traffic.served_mbps_est` | queueing system 视角的已服务完成 | `served_bytes_est` | 仿真总时长 `T_sim` | 系统级已服务速率估计 | 系统是否吃满 offered load、是否仍有积压 |
| `traffic.goodput_mbps` | PHY 成功解码 | `goodput_bytes` | 仿真总时长 `T_sim` | 系统级成功有效吞吐 | PHY 成功率、真实有效吞吐 |
| `traffic.packet_effective_service_rate_mbps` | MAC packet tracker 整包完成 | `sum L_p` | `sum W_p` | 已完成 packet 的平均有效服务速度 | packet 系统时间、长尾排队是否严重 |
| `traffic.packet_effective_service_rate_per_packet_mean_mbps` | MAC packet tracker 整包完成 | `mean(L_p / W_p)` | 无单独 wall-clock 分母 | 先逐包算速率再平均 | 典型 packet 的平均体验、是否存在“多数包还快但少数包极慢” |

最近 `3000 B` 场景里，这几个指标的差异已经很明显：

| Run | Scheduler | `served_mbps_est` | `goodput_mbps` | `packet_effective_service_rate_mbps` | `packet_effective_service_rate_per_packet_mean_mbps` |
| --- | --- | ---: | ---: | ---: | ---: |
| `095056` no-SVD, `0.8 pkt/TTI` | RR | 1012.321 | 894.728 | 0.585 | 29.160 |
| `095056` no-SVD, `0.8 pkt/TTI` | PFQ | 1004.464 | 888.551 | 0.347 | 7.518 |
| `070312` SVD, `0.8 pkt/TTI` | RR | 1377.917 | 1207.815 | 15.741 | 39.468 |
| `070312` SVD, `0.8 pkt/TTI` | PFQ | 1380.238 | 1226.158 | 35.048 | 42.639 |
| `075923` SVD, `1.0 pkt/TTI` | RR | 1668.628 | 1472.826 | 1.791 | 37.407 |
| `075923` SVD, `1.0 pkt/TTI` | PFQ | 1728.233 | 1538.654 | 21.497 | 39.054 |

从这里可以直接看出：

- `served_mbps_est` 和 `goodput_mbps` 是系统 aggregate 速率，所以数值在 `Gbps` 量级
- `packet_effective_service_rate_mbps` 不是 cluster aggregate throughput，它是 packet system time 口径下的平均服务速度
- 在重载、长尾排队明显时，`R_pkt` 会迅速下降
- `R_pkt_mean` 往往显著高于 `R_pkt`，说明“多数包并不慢，但少数长尾包把总 packet system time 拉得很大”

`075923` 下 RR 就是典型例子：

- `goodput_mbps` 仍有 `1472.826 Mbps`
- 但 `packet_effective_service_rate_mbps` 只剩 `1.791 Mbps`
- 同时 `packet_effective_service_rate_per_packet_mean_mbps` 还有 `37.407 Mbps`

这说明 RR 在 `arrival_rate = 1.0 pkt/TTI` 时，并不是所有 packet 都慢，而是出现了明显的长尾 backlog；这和后面看到的 `queue_delay_est_ms`、`expired_packets`、`residual_buffer_ratio` 恰好一致。

## 2. PF 当前新增的“按需分配”优化逻辑

### 2.1 当前逻辑的目标

当前对 PFQ 新增的优化目标是：

- 资源分配只需要覆盖当前业务需求即可
- UE 已经拿到足够支撑当前 queue demand 的 PRG 后，不再继续给它追加 PRG
- 对最后一个可能“超出需求”的 PRG，调度 metric 要降权，credited bytes 也要截断到剩余需求

这意味着 PFQ 不再简单追求“把 PRG 分满”，而是更强调“把有限 PRG 用在当前真正还缺资源的 UE 上”。

### 2.2 当前 PFQ 的基线 metric

当前 queue-aware PFQ 的基本形式可以写成：

`PFQ_i = (R_i^beta / avgRate_i) * queueWeight_i`

其中：

- `R_i` 是当前 PRG 对应 UE 的瞬时 data rate
- `avgRate_i` 是 PF 的长期平均速率状态
- `beta` 是 PF 的速率指数
- `queueWeight_i = 1 + alpha * log2(1 + buffer_i / B_scale)`

也就是说，PFQ 在传统 PF 的基础上，又乘上了一个 buffer-aware 权重：

- UE buffer 越大，权重越高
- 但权重增长是 `log2(1 + x)`，不是线性暴涨

当前默认参数是：

- `buffer_coeff = 0.25`
- `buffer_scale_bytes = max(packetSizeBytes, 1)`
- `demand_cap = on`
- `demand_cap_slack_bytes = packetSizeBytes`
- `intra_tti_decay_coeff = 0.5`

### 2.3 “按需分配”怎么做

对每个待选 UE，先估算当前一个 PRG 可能能带来的字节数：

`predBytes = max(dataRate * T_slot * 0.125, 1)`

然后定义：

- `demandBytes = bufferBytes + slackBytes`
- `remainingBytes = demandBytes - assignedBytes`

其中：

- `bufferBytes` 是该 UE 当前 MAC buffer
- `slackBytes` 是为了避免离散 PRG 粒度下出现“差一点点不够”的保护量，当前默认约等于 `1` 个包长
- `assignedBytes` 是本 TTI 当前已经按 scheduler 记账分给这个 UE 的字节数

接下来分三种情况：

1. 如果 `remainingBytes <= 0`
   - 当前 UE 的 PFQ metric 直接变成 `0`
   - 后续 PRG 不再继续给它

2. 如果 `predBytes > remainingBytes`
   - 当前 PRG 可能会超出剩余需求
   - 那么先把 metric 按比例缩小：
   - `metric = metric * remainingBytes / predBytes`

3. 真正 commit grant 时
   - 当前 UE 本 TTI 的 credited bytes 只累计：
   - `creditedBytes = min(predBytes, remainingBytes)`

此外，当前还有一个 intra-TTI decay：

- 如果某个 UE 在同一个 TTI 已经拿了多个 PRG
- 其后续 PRG metric 会再按 `1 / (1 + decay_coeff * assignedPrgCount)` 衰减

这会进一步抑制“一个 UE 在一个 TTI 内把大量 PRG 连续吃满”的情况。

### 2.4 这里的“严格匹配业务量”需要做一个边界说明

当前实现里，PRG 仍然是离散资源，不能把一个 PRG 物理切成“只发剩余那几百字节”。

因此当前 demand-cap 的准确含义是：

- 一旦 UE 的累计 credited bytes 已达到当前需求，就不再继续给它后续 PRG
- 对最后一个可能超配的 PRG，不做 PRG 物理切分
- 而是通过 metric 降权和 credited-bytes 截断，让这个 UE 只在“确有必要”时才赢得该 PRG

所以更准确的表述不是“把 PRG 精确切到刚好等于业务量”，而是：

- 调度目标改成按需分配
- 超过当前需求后不再继续追加 PRG
- 对最后一个临界 PRG 做降权处理，避免不必要的资源浪费

### 2.5 这个优化现在带来的直接现象

这个逻辑的一个很典型结果，是 PFQ 往往会出现：

- `PRG utilization` 低于 RR
- 但 `served_mbps_est`、`goodput_mbps`、`queue_delay_est_ms` 反而更优

最近实验里已经能看到这个趋势：

| Run | Scheduler | `served_mbps_est` | `goodput_mbps` | `queue_delay_est_ms` | `prg_utilization_ratio` |
| --- | --- | ---: | ---: | ---: | ---: |
| `070312` SVD, `3000B x 0.8` | RR | 1377.917 | 1207.815 | 4.442 | 0.999889 |
| `070312` SVD, `3000B x 0.8` | PFQ | 1380.238 | 1226.158 | 0.322 | 0.847832 |
| `075923` SVD, `3000B x 1.0` | RR | 1668.628 | 1472.826 | 27.096 | 1.000000 |
| `075923` SVD, `3000B x 1.0` | PFQ | 1728.233 | 1538.654 | 1.152 | 0.918005 |

这说明 PFQ 目前不是靠“多用资源”取胜，而是靠“更按需、更高效地使用 PRG”取胜。

## 3. 4T4R + SVD precoding 带来的容量变化确认

### 3.1 平台当前状态

当前平台已经是 `4T4R`：

- BS 端 `nBsAntConst = 4`
- UE 端 `nUeAntConst = 4`

并且当前 precoding 已从 `no precoding` 切换为 `svd precoding`。

这次切换的本质不是“只多了一个小开关”，而是整个 4T4R 调度链路开始真正使用：

- `estH_fr_actUe_prd` 里的 `4 x 4` 信道矩阵
- 通过 SVD 求出的 `sinVal_actUe`
- `prdMat_actUe`
- `detMat_actUe`

然后 layer selection 再基于 singular values 选择实际层数，最后 `TBS` 直接乘上 `nrOfLayers`。

因此从 no-SVD 切到 SVD 后，系统容量提升非常明显是符合代码逻辑的。

### 3.2 层数变化时，物理端口和信道矩阵会不会变化

这里需要明确区分“硬件维度”和“运行时层数”：

#### 不会变化的部分

- 物理发射/接收天线端口配置仍然是 `4T4R`
- BS 端还是 `4` 个发射端口
- UE 端还是 `4` 个接收端口
- 每个 UE/PRG 对应的信道矩阵维度仍然是 `4 x 4`

也就是说：

- 从 `1` 层变成 `3.x` 层，并不是把系统从 `1T1R` 变成 `4T4R`
- `4T4R` 的物理端口和信道矩阵维度本来就已经固定在那里

#### 会变化的部分

- 同一个 `4 x 4` 信道矩阵上，SVD 每个 TTI/PRG 都会重新计算：
  - `sinVal`
  - `prdMat`
  - `detMat`
- layer selection 会根据 singular value 分布动态决定本次实际启用几层
- 因此变化的是：
  - 使用了几个空间模态
  - 每层怎么映射到 4 个物理端口
  - 每层对应的有效空间增益

简化理解就是：

- “端口数”和“矩阵维度”不变
- “怎么用这 4 个端口、一次并行发几层”在变

### 3.3 最近实验里层数的变化

最近几组实验的平均发射层数已经非常稳定：

| `034927` SVD | `2000B`, `0.5 pkt/TTI` | 3.310 | 3.567 |
| `065108` SVD | `2000B`, `0.6 pkt/TTI` | 3.355 | 3.567 |

因此当前最重要的结构性变化就是：

- no-SVD 时基本是单层传输
- 开 SVD 后，平均层数直接抬到 `3.3 ~ 3.55`

这会直接抬升 TBS 和瞬时可服务能力。

4. PFQ 在 SVD 后不一定需要把 PRG 用满，也能达到比 RR 更好的结果
   - 这和前面“按需分配”的优化逻辑是一致的

### 3.6 `arrival_rate = 1.0 pkt/TTI` 时 RR 掉队的原因

`075923` 相比 `070312`，主要变化只是：

- `arrival_rate`: `0.8 -> 1.0 pkt/TTI`
- 包大小仍然是 `3000B`
- offered load 大约从 `1.38 Gbps` 抬到 `1.73 Gbps`

当前 RR 掉队并不是因为它“不够忙”，恰恰相反：

- `PRG utilization = 1.0`
- `scheduled_ratio_mean = 0.761`

它的问题是：

- 即使已经把 PRG 基本打满
- 平均层数也已经在 `3.5` 左右
- 但 RR 的有效服务能力仍然没有贴住 offered load

| residual buffer ratio | 0.013094 | 0.000576 |
| UE throughput p5 Mbps | 35.033 | 46.916 |
| UE throughput Jain | 0.992252 | 0.999787 |
| PRG utilization ratio | 1.000000 | 0.918005 |
| global TB BLER | 0.1160 | 0.1117 |

因此 RR 当前掉队的直接原因可以概括成：

1. RR 虽然资源打得很满，但没有把这些机会足够高效地转化成有效服务量
2. PFQ 依靠 demand-cap + queue-aware 权重，在重载下更能把 PRG 放到真正还缺业务量的 UE 上
3. RR 的 PHY 条件也没有形成反超，平均层数只略低于 PFQ，但 `BLER` 仍略差
4. 一旦 offered-served 出现持续缺口，问题首先表现在：
   - `packet_effective_service_rate_mbps` 暴跌
   - `queue_delay_est_ms` 抬升
   - `expired_packets` 开始出现
   - `residual_buffer_ratio` 持续积累
   - `ue_throughput_p5_mbps` 和公平性恶化

### 3.7 当前提升来源总结

当前这轮平台能力提升主要来自两部分叠加：

1. `4T4R + SVD precoding`
   - 在固定 `4 x 4` 信道矩阵上做 SVD
   - 使实际发射层数从 `1` 层提升到平均 `3.x` 层
   - 直接抬升 TBS 和可服务吞吐能力

2. PFQ 的按需分配优化
   - 不再把 PRG 简单地持续给已经接近满足需求的 UE
   - 让有限 PRG 更集中地服务仍有实际 backlog 的 UE
   - 所以在 `PRG utilization` 更低的情况下，仍能拿到更好的 `served`、`goodput`、`queue delay` 和 `R_pkt`

综合来看，当前容量大幅提升是符合常理的：

- no-SVD -> SVD 带来的是空间复用能力释放
- PFQ demand-cap 带来的是资源使用效率提升
- 一旦系统从“过载区”跨到“接近可承载区”，吞吐、时延、TTL 过期、低分位吞吐等指标都会出现明显的非线性改善

## 4. 本次确认结论

- 新增的 `traffic.packet_effective_service_rate_mbps` 和 `traffic.packet_effective_service_rate_per_packet_mean_mbps` 已经能从 packet 视角补充传统 aggregate throughput 指标无法直接反映的长尾排队信息。
- `traffic.served_mbps_est`、`traffic.goodput_mbps`、`traffic.packet_effective_service_rate_mbps` 三者不能混为同一个“吞吐量”，它们分别对应 queue-drain、PHY success、packet system time 三种不同口径。
- 当前 PFQ 已经实现“按需分配”的优化目标，但精确实现方式是“超过需求后停止继续追加 PRG，并对最后一个临界 PRG 降权和截断记账”，不是把 PRG 物理切分成任意小粒度。
- 平台当前已经稳定工作在 `4T4R + SVD precoding` 模式下，平均层数从 `1` 提升到 `3.3 ~ 3.55`，这是最近容量提升最核心的来源。
- 层数变化时，物理端口数和信道矩阵维度不变，变化的是同一 `4 x 4` 信道矩阵上的 precoder、detector、singular values 和实际启用层数。
- 近期重载实验表明，PFQ 在高负载下已经明显优于 RR；RR 的掉队首先表现在 `R_pkt`、queue delay、residual buffer、TTL expiry 和低分位吞吐上。
